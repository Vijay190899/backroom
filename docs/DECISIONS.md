# Decision Log

Short ADRs. Newest at the bottom. Format: **Decision**, then *why*, then *alternatives*.

1. **Mock portals instead of real sites.** *Why:* reproducible benchmarks, no credentials, legal, can't break during the interview, and the chaos engine is only possible on sites we control. *Alt:* real sandbox sites (flaky, ToS issues).
2. **No bot-protection evasion.** *Why:* ToS and ethics; not a durable strategy. Human handoff is better UX. *Alt:* stealth browsers (rejected).
3. **Own browser-agent loop on Playwright + ARIA snapshots.** *Why:* skill compilation and healing are the differentiator and need full control and metrics. *Alt:* browser-use, Stagehand.
4. **Temporal graph in Postgres (custom) instead of Graphiti/Neo4j.** *Why:* one datastore, bitemporal SQL is simple, deterministic writers for structured data (no per-row LLM extraction cost), fewer moving parts to break. *Alt:* Graphiti + FalkorDB (richer, but LLM-heavy ingest and another service).
5. **"Agents for judgment, code for math."** *Why:* trust. LLMs never originate numbers, and the number guard enforces it. *Alt:* LLM-computed insights (hallucination risk).
6. **Cheap-by-default model ladder (Haiku 5.5 worker, Sonnet 5.5 planner), env-swappable.** *Why:* demo cost and latency; also a cost-aware multi-model talking point. *Alt:* Opus 5.5 everywhere (≈2× Sonnet; benchmark it in B4). *Amended by ADR-9:* the provider is swappable too.
7. **Vercel (web) + AWS Lightsail (backend, docker compose) + Caddy/sslip.io.** *Why:* their stack (Vercel + AWS), ~$12/mo, one box, two-minute rollback via snapshot. *Alt:* App Runner/ECS (more setup), Fly/Hetzner (not their stack).
8. **A single task runner: root `package.json` scripts (pnpm) on top of a uv workspace.** *Why:* one set of commands (`pnpm check | seed | bench | dev | e2e | probe:llm`) that works on Windows and Linux, in CI and on the server; `make` isn't available on Windows by default. *Alt:* Makefile, `just` (not installed), per-service READMEs (drift).
9. **LLM provider = OpenRouter by default, Anthropic direct as a switch (`LLM_PROVIDER`).** *Why:* the user's choice. One key, model flexibility for B4, same per-token Claude prices (verified 11 Nov). We keep a single code path: the official `anthropic` SDK against OpenRouter's Anthropic-compatible endpoint. *Trade-offs:* ~5.5% credit fee; Anthropic beta features (server-side fallbacks etc.) are off on OpenRouter and handled by the client escalation ladder; other features are confirmed by `pnpm probe:llm`, with results recorded here. *Alt:* the OpenAI-compatible OpenRouter API (second code path, loses Anthropic-native features); Anthropic direct only.
10. **Postgres is reached through a synchronous psycopg pool, called from worker threads.** *Why:* on Windows, psycopg's async mode needs the selector event loop while Playwright needs the proactor loop; one process can't have both. A sync pool behind `run_in_threadpool` works on Windows and Linux alike. *Alt:* async psycopg (breaks local dev on Windows), a separate browser process (more moving parts).
11. **The LLM spend ledger is an append-only JSONL file (`var/llm_ledger.jsonl`, `LLM_LEDGER_PATH`).** *Why:* the budget guard and the capability probe must work before the database exists, and one API process is the only writer. Per-run costs for the UI are stored with the run in Postgres (M2). *Alt:* a Postgres table (couples the probe to the DB).
12. **Theme switching is a 20-line inline script plus a `useSyncExternalStore` toggle, not `next-themes`.** *Why:* no flash of the wrong theme, no client-side script warning under React 19, one less dependency. *Alt:* `next-themes`.
13. **shadcn/ui is installed in its current default style (`base-nova`, Base UI primitives), with its colour variables mapped onto our `--t-*` tokens.** *Why:* the tokens in `apps/web/src/styles/tokens.css` stay the single source of colour; they are prefixed because shadcn already owns `--accent` and `--muted`. The primary button is ink, not caramel: white on caramel is only 3.1:1.
14. **Deploy images are built in GitHub Actions and pulled by the server (GHCR); nobody builds them locally.** *Why:* the api image is 4.3 GB (Playwright + Chromium), which a 2 GB Lightsail box and a light laptop cannot build comfortably, and a CI build is reproducible. *Alt:* build on the server (risk of running out of memory on deploy night).
15. **Two-machine workflow: light tasks on a laptop without Docker, heavy tasks on the main PC.** *Why:* the laptop is too light for Docker and Chromium, but most remaining work is plain code. Split by weight, contract-first (L0), with directory ownership and separate sync logs to avoid merge conflicts (HANDOVER §9). The laptop uses a free hosted Neon Postgres where it needs a database, and `pnpm dev:lite` otherwise. *Alt:* everything on the PC (serial; not enough time before the interview).

## Laptop deviations (L-n)

Written on the laptop. Every place where the laptop's work departs from the PRD, ARCHITECTURE, BUILD_PLAN or HANDOVER §9 gets an entry here, with the reason. Append-only; the PC renumbers on merge (HANDOVER §9.4).

- **L-1 (L10). The laptop committed `bench/results/provider_probe.json`, a PC-owned path.** *Why:* task L10 says to commit it, and the probe ran on the laptop because that's where the key was first added. *Effect:* one new file; no PC file was edited.
- **L-2 (L0). Branches are stacked (`l0` on `l10`, `l1` on `l0`, `l2` on `l1`), not each cut from `main`.** *Why:* each task needs the one before it (L1 imports the L0 contracts), and both L10 and L0 add an entry to `docs/sync/laptop.md`; separate branches would conflict there. *Effect:* merging the newest branch brings in all earlier ones, in order.
- **L-3 (L0). Wiring outside the laptop's ownership, so the contract check runs everywhere:** a `check:web` script line in the root `package.json`, a `contracts` script in `apps/web/package.json`, `allowImportingTsExtensions` in `apps/web/tsconfig.json`, and one step in `.github/workflows/ci.yml`. *Why:* a contract that can drift silently is worse than none. The check runs the zod mirror against the shared fixtures with plain `node` (no build step), and that needs these four lines. *Alt:* a PC follow-up (slower; the check would be missing until then).
- **L-4 (L0). New shared paths that are not in the HANDOVER ownership table:** `services/api/backroom_api/contracts/` (pydantic contracts), `services/api/migrations/` (SQL migrations), `services/api/scripts/gen_fixtures.py` and `apps/web/src/fixtures/`. *Why:* L0 asks for these artefacts but names no location except `skills/schema.py` and `0001_memory.sql`, so the laptop chose them. *Ask:* the PC adds them to the "shared, change only through L0" row.
- **L-5 (L0). All portals run in one service under path prefixes (`/grainline`, `/tilldesk`, `/localboard`), so a run's navigation allowlist is origin + path prefix, not origin alone.** *Why:* ARCHITECTURE §1 and §4 define one portals service on one host (`portals.<ip>.sslip.io`); separate origins would need more Caddy hosts and certificates. PRD §8.1 says "only the target portal origin", which this tightens to the prefix.
- **L-6 (L0). The skill heal semantics go further than PRD §8.2/F3:** a run that heals several steps produces **one** new version, stored only if the run succeeds with every postcondition passing; a diff can insert or delete steps (`StepChange.op`), not only change fields. *Why:* a cookie banner (chaos seed 7) needs an extra dismiss step, and a failed run must not leave a broken version behind.
- **L-7 (L0). The memory schema adds `invalidated_at` and `superseded_by` to `fact`** (ARCHITECTURE §7 sketch has neither). *Why:* without `invalidated_at` the graph is not truly bitemporal: supersession overwrites `valid_to`, so "what did we believe at time r" would return wrong answers. `superseded_by` makes the fact inspector's provenance a single lookup.
- **L-8 (L0). API routes and shapes not in the ARCHITECTURE §3 table:** `POST /runs/{id}/undo`, `POST /runs/{id}/human`, SSE events for `GET /brief/today?regenerate=1`, the golden-run frame index (`GoldenFrame`), and `ContextPack` on `RunSummary`. *Why:* PRD F1 (streamed brief), F2 (Undo), F4 (context pack shown per run), F7 (frames in golden runs) and §8.1 (`ask_human` handoff) require them, but no route or shape was defined for them.
- **L-9 (L0). The migration `0001_memory.sql` has not been run on a real Postgres yet.** *Why:* the laptop has no Docker, a Neon database is not set up yet, and downloading a SQL parser was blocked by the session's permission check. It was reviewed twice (author and auditor). *Next:* the PC applies it in H1, or the laptop on Neon in L5.
- **L-10 (L1). TOTP and invoice PDFs are hand-written (RFC 6238 in ~15 lines; a one-page PDF writer) instead of `pyotp` and WeasyPrint/ReportLab (ARCHITECTURE §4).** *Why:* no new third-party packages (no lockfile churn for the PC), byte-for-byte deterministic PDFs for tests, and a smaller portals image. TOTP is checked against the RFC 6238 test vector. *Alt:* the libraries, if invoices ever need layout beyond one text page.
- **L-11 (L1). `pydantic-settings` added to the portals package.** *Why:* the portals need the same `.env` settings as the api (credentials, admin token, `DATA_SEED`). The package was already in the lockfile via the api, so `uv.lock` changed by 2 lines.
- **L-12 (L1). Four labels added to the L0 label contract** (`update_qty`, `remove`, `prev_page`, `next_page`). *Why:* the cart and pagination controls exist in the spec (PRD §3), and every visible control label must go through the contract so chaos can vary it. Proposed to the PC in the sync log, since L0 is not acknowledged yet.
- **L-13 (L1). With `GRAINLINE_TOTP_SECRET` empty, the TOTP secret is derived from `DATA_SEED`** (`backroom_portals.totp.default_secret`). *Why:* `.env.example` says "the seed step generates one", but `pnpm seed` (L4/H1) doesn't exist yet, and the portal must work by hand now. *Effect:* the agent's vault must use the same rule until the seed writes a secret.
- **L-14 (L1). A fresh login empties the Grainline cart** (real shops usually keep it). *Why:* a skill replay must never inherit leftovers from an earlier run, otherwise the `orders.last.lines.0.sku` postcondition can pass or fail by accident.
- **L-15 (L1/L2). Chaos varies control labels only; headings and messages stay English at every seed.** *Why:* PRD/ARCHITECTURE describe "label synonyms and language (EN/DE)" on controls; the agent acts on controls, and translating every heading would triple the template work for no test value. *Effect:* seed 7 shows German controls on English pages.
- **L-16 (L0). Chaos seed 7 is pinned to exactly German labels + top-bar nav + cookie banner, and nothing else.** *Why:* DEMO_SCRIPT 1:40 promises exactly these, and the demo heal must be predictable; other seeds stay random.
- **L-17 (process). The laptop opens draft PRs so CI runs on its branches.** *Why:* CI only runs on `main` pushes and pull requests, and the laptop must not push to `main`. The PC still merges with `git merge --no-ff` (HANDOVER §9.4), which closes the drafts.
- **L-18 (L2). One more label in the contract: `open_menu` ("Open menu" / "Show navigation" / "Menü öffnen") in `INTERSTITIAL_LABELS`.** *Why:* the `nav_position=hamburger` variant (ARCHITECTURE §4) needs a visible toggle, and every visible control label must go through the contract. Not "Menu": that would clash with TillDesk's "Menu" nav link.
- **L-19 (L2). Shared template macros (`services/portals/backroom_portals/templates/macros.html`) plus a per-request `Look` object render every chaos family.** *Why:* nine families × every page would otherwise mean editing each template nine times; with macros each family is written once and TillDesk (L3) gets chaos for free. *Effect:* every portal template must import the macros `with context` (CONTRACTS §3).
- **L-20 (L2, extended in L3). `list_layout` (table ↔ cards) applies to the Grainline catalog, the invoice list and the TillDesk menu; order history, cart, checkout and dashboard always stay tables.** *Why:* ARCHITECTURE §4 lists layout permutations without naming pages. The product, invoice and menu lists are what the B1 tasks scan; cards on a cart would not change any skill step.
- **L-21 (L2). Interstitial dismissal is a browser cookie per (portal, seed, kind), not server state; `/_admin/reset` does not clear it.** *Why:* that is how real consent banners behave, and it keeps the server stateless per visitor. *Effect:* the agent runner must use a fresh browser context per run (CONTRACTS §3 rule 1), or a reused context skips the banner and a healed "dismiss" step fails.
- **L-22 (L2). Agent-runner rules added to the contract (fresh context, wait for `[aria-busy]` to clear, open the hamburger, links submit via JS).** *Why:* without them the `interstitial`, `delayed_render`, `nav_position` and `control_kind` variants turn into false B1 failures; these are runner obligations the PC needs to know about, not portal bugs.
- **L-23 (L2). The api's `POST /chaos` forwarding route (ARCHITECTURE §3) is not built on the laptop.** *Why:* it lives in `services/api/backroom_api/routes/`, next to the PC's run routes, and needs the api's HTTP client and settings; the portal side (`/_admin/chaos`) and the shared models are done. *Ask:* the PC adds it with H4. The existing test already keeps the api's and portals' chaos models identical.
- **L-24 (L2). Risk, not yet a change: a real seed-7 heal will touch at least five steps, not the two in the fixture.** At seed 7 every control label is German, so "Sign in", "Verify", "Quantity", "Add to cart" and "Place order" all miss, and a cookie-dismiss step must be inserted. *Why logged:* DEMO_SCRIPT 1:40 expects a quick heal. *Options for the PC (H3):* time a live heal first; if it's slow, have the compiler add label/css fallbacks, or narrow seed 7 to fewer German labels (which changes L-16).
- **L-25 (L2). `services/portals/tests/__init__.py` makes the portal tests a package.** *Why:* the chaos tests reuse the Grainline test helpers through a relative import, instead of duplicating them.
- **L-26 (L3). Localboard (P1) is not built.** *Why:* HANDOVER §9.1 says "Localboard later if time", and PRD §6 puts Localboard first in the cut order. The data pipeline (L4) and the memory and brief work are on the critical path. *Effect:* the rainy-Saturday card stays a recommendation only (PRD F1 card 3, P0 variant). Decide at the M3 gate.
- **L-27 (L3). The TillDesk menu (8 items, their names and starting prices) is fixed in `tilldesk/store.py` (`MENU`).** Only Franzbrötchen €3.20 came from the spec. *Why:* the portal needs a menu now; CONTRACTS had prices "belonging to L4/L1". *Effect:* the data pipeline (L4) maps sales onto these ids and prices, rather than the other way round.
- **L-28 (L3). Draft/publish model: saving a price makes a draft, and "Publish menu" publishes every draft. Publish is always shown, and a fresh login drops unpublished drafts.** *Why:* ARCHITECTURE says "edit price, publish". Always showing Publish keeps retries and B1 repeats (which save the price already live) from losing their Publish step. Dropping drafts at login stops a failed run's draft from going live in the next run.
- **L-29 (L3). Row-scoped links use `aria-label = "<label> <row name>"`, so their accessible name differs from their visible text** ("Edit" shown, "Edit Franzbrötchen" announced). *Why:* eight identical "Edit" links would be ambiguous to a role+name locator. *Effect for the PC:* skills target the full name, or `goto` the stable edit URL (CONTRACTS §4).
- **L-30 (L3). Runner rule: match accessible names exactly** (CONTRACTS §3 rule 5). *Why:* Playwright matches names by substring by default, so "Menu" also matches "Publish menu", and "Speisekarte" also matches "Speisekarte veröffentlichen".
- **L-31 (L3). `GET /tilldesk/` (redirects to the menu) was added to `TILLDESK_ROUTES`, and `/_admin/state/{portal}` now returns `GrainlineState | TillDeskState`.** *Why:* a bare portal URL should land somewhere useful, and the change-price postcondition reads TillDesk state.
- **L-32 (L4). Next Saturday's forecast is overwritten to 9 mm of rain (`source` ends in `+demo_override`).** *Why:* PRD F1 card 3 needs a rainy Saturday on demo day, and the real forecast can't be booked. It is labelled in the table and in the manifest notes, so nothing claims it's a real forecast.
- **L-33 (L4). The rainy-Saturday effect is calibrated, not a flat multiplier: each rainy Saturday (≥ 2 mm) keeps a seeded 86% of the mean of the dry Saturdays within ±3 weeks.** *Why:* DATA.md describes "a seeded multiplier (−14%)", but over this window the re-based sales double in volume and there are only ~5 rainy Saturdays. A flat 14% drop came out as −9%, and after re-basing even +11%. Calibrating against nearby Saturdays makes the data show about −14% (−13.9% measured) whatever the trend. Still synthetic, and labelled as such.
- **L-34 (L4). Sales prices are the TillDesk menu prices (EUR, VAT included), not the Maven USD prices converted ("USD→EUR with café-style rounding" in DATA.md).** *Why:* revenue and margins must match what the till charges (L-27), or the margin story wouldn't reconcile. The source USD price is kept in `source_unit_price_usd`.
- **L-35 (L4). The sales window ends yesterday, not "today" (DATA.md).** The source is first trimmed by up to 6 days, so that a whole-week shift lands its last day on yesterday's weekday. *Why:* today's sales aren't complete yet, and a 7-day velocity needs seven full days.
- **L-36 (L4). A small stdlib `.xlsx` reader (`backroom_data/xlsx.py`) replaces a library such as `openpyxl`.** *Why:* the Maven file is one sheet of plain values, and the stdlib reader streams 149k rows in ~2 s without a new dependency. Inline-string cells and extra sheets are not supported (the source has neither).
- **L-37 (L4). Grainline's usual oat-milk order went from 24 to 10 cartons (in `backroom_portals/grainline/catalog.py`, a laptop-owned L1 file).** *Why:* with 220 ml per oat latte the café now uses ~38 L a week. A larger usual order made the simulated stock rise, or zig-zag below zero, before the demo's "2 days left". At 10 the stock falls steadily to the stock-out, and the agent's 24-carton reorder is the fix. *Effect:* the seeded order history shows 10±1 oat cartons per order.
- **L-38 (L4). The root `pyproject.toml` `testpaths` gained `data/tests`.** *Why:* otherwise `pnpm check` and CI never run the data tests. It's one line in a "shared, careful" file.
- **L-39 (L4). `backroom-data` depends on `backroom-portals` (a workspace package), plus `duckdb>=2.0,<3` and `pyyaml`.** *Why:* the data must use the portal's own price history, seeded orders and menu, so imports avoid copying them; DuckDB is the planned analytics store and writes the Parquet files. *Effect:* `uv.lock` changes; the PC re-locks on merge.
- **L-40 (L4). `backroom-data all` writes Parquet plus `preferences.json` and does not load Postgres.** DATA.md says `pnpm seed` also loads Postgres. *Why:* loading needs the database and the migration runner, which are the PC's (H1); the laptop's part is "writes the Parquet files" (HANDOVER §9.1 L4). Preferences become memory episodes when the PC or L5 loads them.
- **L-41 (L4). Inventory covers only the last 28 days, the window that has real Grainline orders; the opening stock is solved so oat milk ends at exactly 2.0 days of 7-day velocity, and other SKUs keep at least 4 days.** *Why:* the portal seeds 28 days of orders; simulating months without deliveries gave absurd opening stocks (765 L), which would be bad ground truth for B3.
- **L-42 (L4). The synthetic fallback has its own volume (~240 lines a day, no trend), unlike the Maven store (~110 rising to ~220).** *Why:* it is a schema-compatible stand-in so the demo runs without the download; the manifest notes mark it SYNTHETIC. The story numbers that matter (unit costs, 2 days of oat milk, 9 mm, −14%) are built in either way.
- **L-43 (L6). The oat-milk reorder is computed as one week of cover: 28 cartons, €44.52 on today's data, not the "24 × €1.59 = €38.16" in PRD F2 and the first fixtures.** *Why:* PRD F1 says the card numbers are illustrative and the detectors compute the real ones; 7 × 5.47 L/day − 10.9 L in stock needs 28 cartons. The fixtures, contract comments and L-37's wording were updated to match. *Effect:* the demo's result summary will read "28 × 1L oat milk, €44.52".
- **L-44 (L6). Pricing rule: the proposed price is the lowest 10-cent price that reaches the margin target + 1.5 points; under an owner's cap it is the highest 5-cent step within the cap, never below today's price.** *Why:* this reproduces PRD F1/F4 from the data (€3.20 → €3.60 at 72%; capped at 8%: €3.45, +7.8%, 70%). The buffer keeps one more cost bump from sinking the margin again. All rounding is half-up.
- **L-45 (L6). Weekly impact is defined per kind (stock-out: last week's sales of items that need the ingredient; margin: units × price rise; weather: one shift's labour), and cards are ranked by it.** *Why:* PRD F1 ranks "by € impact" but doesn't define it. These are three different kinds of euros, so the stock-out card usually ranks first. The definitions are in CONTRACTS §6.
- **L-46 (L6). Card thresholds:**
  - stock-out under 3 days of stock;
  - margin card only when the raw margin is below target and the cost rose over 28 days;
  - weather card only when next Saturday has ≥ 2 mm of rain, rainy Saturdays are at least 5% weaker, and at least two 14:00–18:00 shifts are planned.
  *Why:* the PRD gives the stories, not the trigger rules; these are the smallest rules that produce exactly the three demo cards on the built data.
- **L-47 (L6). `duckdb>=2.0,<3` added to the `backroom-api` package; the analytics tests import `backroom-data` (a workspace sibling) to build test data.** *Why:* detectors run DuckDB SQL inside the api (ARCHITECTURE §3). The tests use the real pipeline offline instead of hand-made Parquet files. *Effect:* `uv.lock` changes; the PC re-locks on merge.
- **L-48 (L6). "Footfall" on the weather card is counted as distinct `transaction_id`, which is one line item per id in the Maven data.** *Why:* the source has no basket id; the effect is relative (rainy vs nearby dry Saturdays), so the unit doesn't change the percentage.
- **L-49 (L6). `as_of` timestamps are midnight Europe/Berlin, and a detector run must use the date the data was built for.** *Why:* every table is relative to the build's "today"; any other date would mix past and future rows without an error.
- **L-50 (L5). Writers of one fact key are serialised with a Postgres advisory transaction lock (`pg_advisory_xact_lock` on subject|predicate[|object]), not only `FOR UPDATE`.** *Why:* the audit showed on Neon that a row lock lets two concurrent writers leave two open facts (there's no row to lock yet, and READ COMMITTED re-checks). A two-connection test now proves only one fact stays open.
- **L-51 (L5). Back-dated facts are refused (`OutOfOrderFactError`), and re-asserting a value that is already known (open or since superseded) is a silent no-op.** *Why:* supersession must move forward in valid time (a correction on the same date can't satisfy `valid_to > valid_from`). The no-op makes every writer idempotent, so replaying the invoice history adds nothing.
- **L-52 (L5). New predicates and a many-valued set:**
  - `orders_via`, `sells_via`, `works_at`, `has_rule`, `unit_price_eur_each`, `weather`, `observed_in`;
  - many-valued: `uses_ingredient`, `has_preference`, `has_rule`, `works_at`.
  - Business rules (the 70% margin target) are `preference` entities linked by `has_rule`.

  *Why:* CONTRACTS §8 lists only a starting vocabulary and says to extend it; these are the smallest additions that carry the demo world, the verifier's rules and the time context.
- **L-53 (L5). Recipe amounts are stored as `{"grams": …}` / `{"ml": …}` / `{"pcs": …}`.** *Why:* that's the shape CONTRACTS §8 and the shared fixture use; the Parquet table keeps kg/l.
- **L-54 (L5). Context packs estimate tokens at 3 characters per token (no tokenizer call), and the business's standing preferences and rules always lead the pack.** Relevance is hop distance, then recency, then confidence. *Why:* a per-pack token count call costs a request; 3 chars/token errs high for ids, JSON and digits, so the budget holds. Standing rules first means the learned "max 8%" cap reaches every brief (PRD F4).
- **L-55 (L5). The demo's live invoice ingest works by holding back every invoice from the butter price change on (`invoices_from_price_change`) and then ingesting the first (`write_invoice`).** *Why:* PRD F4's acceptance ("ingesting a Grainline invoice creates superseding price facts") needs an invoice that memory hasn't seen yet. The PC wires it to `POST /memory/ingest/invoice`; PDF text extraction (the LLM extractor) is separate.
- **L-56 (L5). The laptop has no migration runner; the tests apply `0001_memory.sql` themselves into a throwaway schema on Neon, and skip when no database is reachable (so CI doesn't run them).** *Why:* the runner is the PC's (H1), and CI has no Postgres. The tests ran green on Neon (Postgres 18.6, pgvector 0.8.6) and leave no schemas behind.
- **L-57 (L5). The memory graph holds ~60 nodes (business, menu, ingredients, staff, preferences, recent weather, holidays), not the ~300 PRD §12 benchmarks the graph library against.** *Why:* that's the real size of the demo world. The UI can still benchmark at 300 with generated nodes; shifts, skills and insights join the graph when runs and briefs write them.
- **L-58 (L7). The verifier only keeps or vetoes; code does every adjustment.** PRD §8.4 lets it "veto or adjust within the rules". Code re-proposes prices under a learned cap and schedules orders on allowed days, so no model ever produces a number.
  - A veto must cite a known preference or business rule.
  - A veto citing a rule code already enforces, and the card satisfies, is overruled and logged.
  - With no rules the verifier isn't called.
  *Why:* in a real run, Haiku vetoed a Friday reorder under the Tue/Fri rule; model judgment must not override checked arithmetic.
- **L-59 (L7). Number-guard rules go beyond CONTRACTS §6's first draft:**
  - euro amounts keep their cents;
  - "/kg" and "/l" must match per-unit prices;
  - unit words after bare numbers are enforced;
  - a written sign must agree;
  - number words count, fractions in words never match;
  - clock times and years always fail.

  *Why:* each closes a false accept the audit found. The remaining limitation (correct numbers used for the wrong thing or direction) is written into CONTRACTS §6.
- **L-60 (L7). When the planner is unusable (refusal, timeout, API error, spent budget), the brief shows the top 3 candidates by impact in template copy; when the verifier is unusable, cards are kept unverified.** Rank otherwise follows the planner's order. *Why:* PRD G6 "doesn't break"; a brief must always load, and the template copy passes the guard by construction.
- **L-61 (L7). `GuardResult.passed` means "the model's copy passed" (first try or after its one regeneration); False means the card shows template copy.** *Why:* every shown number is verified either way, so a field that was always True would make B5's pass rate 100% by construction.
- **L-62 (L7). Brief streaming: `BriefSkeleton` is sent before any model call, and cards are sent after the verifier, not one by one as each passes the guard.** *Why:* the verifier may still veto a card, so streaming it earlier could show a card that then disappears. The planner call itself is one structured-output request, not streamed.
- **L-63 (L7). Action ids hash the candidate and its final params (`action_id(candidate_id, params)`).** *Why:* after "max 8%" the €3.45 card must not reuse the €3.60 card's id, or approve and reject idempotency would hit the stale action.
- **L-64 (L7).
