# Backroom — Product Requirements Document

> **One line:** the engine under "Approve all". Backroom is an agentic back office for a local café. It finds money in the business data, explains it with evidence, and carries out the fix in the owner's real web tools. It gets faster, cheaper and more aligned with the owner every time it runs.

## 1. Why this exists

Super44's live product already shows the conversational front end: a morning brief with "Approve all", review insights, profit bridges, recipe costing and rotas. Their JD names the hard problems underneath it:

1. **Browser automation that actually works.** Reliable agentic action across arbitrary web interfaces, including auth.
2. **Multi-agent orchestration** across merchant tools, with expert context.
3. **Memory and context** that compound over time.
4. **Agentic self-improvement**: systems that get smarter from every interaction.
5. **UX for agentic systems**, where AI takes action and is simpler than ChatGPT.

Backroom is a working, measured slice of **all five**. It deliberately does not clone their homepage. It shows the machinery and proves it with numbers.

### The pitch, in one sentence for the interview
> "Your homepage has an 'Approve all' button. I built what happens after the owner taps it, and a benchmark showing it doesn't break when the website it's driving changes."

## 2. Goals and non-goals

### Goals (what must be true on Friday)
- **G1, Acts, not suggests.** Approving an action makes a browser agent carry it out live in a merchant web portal, with login and 2FA, while the owner watches.
- **G2, Self-improving.** Repeat tasks get faster and cheaper (compiled skills). Broken skills repair themselves when the site changes (healing). Owner rejections become rules the system obeys (preference learning).
- **G3, Compounding memory.** A temporal knowledge graph of the business where facts have validity windows, supersede each other, and feed compact, token-budgeted context to agents.
- **G4, Trustworthy numbers.** Every € figure shown to the owner was computed by code (SQL/Python), never generated by an LLM. This is enforced by a number guard.
- **G5, Measured.** A public benchmark page with real, reproducible numbers: success rate under chaos, latency, $/task, learning curve, memory-vs-baseline accuracy and tokens.
- **G6, Doesn't break.** Deployed, monitored, rate-limited and budget-capped, with an offline replay fallback so the demo survives a dead API or bad Wi-Fi.
- **G7, Beautiful.** Calm, warm, premium UI that works on a phone (owners live on phones) and on a projector.

### Non-goals
- Real merchant integrations or real credentials. We build realistic **mock portals** we control.
- **Bot-protection or Cloudflare evasion.** Out of scope on purpose. We handle legitimate auth (sessions, TOTP) and a human-in-the-loop handoff for CAPTCHAs.
- Real WhatsApp, iOS or Android. At most a WhatsApp-style mobile view (P2).
- Multi-tenant auth, billing, onboarding.
- Collecting any personal data. All data is open or synthetic, and labelled as such.

### Data (open or synthetic, no collection). Details in [DATA.md](DATA.md)
- **Sales:** Maven Analytics "Coffee Shop Sales" (~149k transactions, one store), converted to EUR and shifted to Bonn dates with weekdays preserved.
- **Weather:** Open-Meteo historical and forecast data for Bonn (free, no key).
- **Holidays:** Nager.Date German public holidays (NRW).
- **Recipes and bill of materials:** hand-authored YAML (e.g. a latte uses 220 ml oat milk and 18 g beans).
- **Supplier price history and invoices:** generated by Grainline, with scripted events (butter +16% on day −9, oat milk +9% on day −3).
- **Staff and rota:** synthetic.
- **Owner preference history:** seeded episodes (e.g. "orders from Grainline only on Tue/Fri"). No price-cap preference is seeded; the demo learns it live (F4).

## 5. Core flows (user stories with acceptance criteria)

### F1. Morning brief (P0)
As Lena, I open Backroom and see **Today**: up to 3 action cards, ranked by € impact.

- Each card shows a title, the € impact (weekly), a one-sentence why, evidence chips (tap to see the SQL result, the facts, the chart), the target portal, and the buttons **Approve** / **Review** / **Not now**.
- There is an **Approve all** button that runs the actions in sequence.
- Seed cards for the demo (numbers are illustrative; the detectors compute the real values from the data):
  1. **Reorder oat milk.** The stock-out forecast says 2 days left at current velocity. Scheduled for the next allowed order day (seeded Tue/Fri preference). Executes on Grainline.
  2. **Fix Franzbrötchen margin.** The butter invoice is +16%, butter is €0.55 of the €0.93 unit cost, so cost rises to €1.02 and margin falls from 71% to 68%, below the 70% target. Proposes €3.20 → €3.60 (+12.5%, margin 72%). Executes on TillDesk. This is the card Lena rejects in the demo (F4).
  3. **Rainy Saturday.** The forecast is 9 mm of rain and history shows −14% footfall on rainy Saturdays. Proposes trimming one 14:00–18:00 shift (P0, shown as a recommendation) or posting a "rainy-day special" on Localboard (P1, executable).
- **AC:** the brief loads in < 1.5 s from cache and in < 15 s on a cold generation (streamed skeleton → cards). Every number on a card passes the number guard (§8.4).

### F2. Run theater (P0). The money shot
As Lena, after approving, I watch the agent work.

- Split view. **Left:** a step timeline (intent, action, mode badge **EXPLORE / REPLAY / HEAL**, duration, tokens, $). **Right:** the live browser stream (CDP screencast) with an agent-cursor overlay on the element being acted on.
- A ticker shows elapsed time, LLM calls, tokens, $ spent and the skill version.
- On completion: a result summary (e.g. "Order #GW-10482 placed, 24 × 1L oat milk, €38.16, arrives Thu") with an **Undo** if the portal supports it (cancel order / revert price).
- A **Chaos** toggle (seed picker) re-skins the target portal before the run, to show healing live.
- **AC:**
  - Warm replay of "reorder item" finishes in < 5 s wall time with 0 LLM calls.
  - Under chaos, the run heals or escalates to a human handoff. It never "succeeds" silently with the wrong outcome; postconditions are verified.
  - Approving the same action twice never double-orders (idempotency key).

### F3. Skill learning and healing (P0)
- First time a task runs: an **EXPLORE** run. The LLM agent drives the browser over the accessibility snapshot.
- On success, the trajectory is **compiled** into a parameterised skill (JSON): steps with semantic locators, fallbacks, pre/postconditions, and secret placeholders.
- Later runs: **REPLAY** deterministically (Playwright), with no LLM.
- When a step's locator or postcondition fails: **HEAL**. Try the locator fallbacks → healer model (`LLM_HEAL_MODEL`) with snapshot + step intent → escalation model (`LLM_ESCALATION_MODEL`) with a screenshot → `ask_human`. The healed step is written as a new skill version, and the UI shows a diff ("Step 4: `button 'Add to cart'` → `button 'In den Warenkorb'`").
- **AC:** the skill registry page lists skills with version history, success rate, mean latency and mean $; it diffs versions.

### F4. Memory (P0)
- `/memory`: an interactive graph (entities as nodes, facts as edges) with a **time slider** ("as of"). Dragging back shows superseded facts (butter €7.10/kg → €8.24/kg, 9 days ago).
- A fact inspector shows the value, validity window, source (invoice PDF / approval / chat), confidence and the episodes that produced it.
- Every agent run shows its **context pack**: which facts were retrieved, token count, and the budget.
- **AC:**
  - Uploading or ingesting a new Grainline invoice PDF creates superseding price facts within 10 s. The relevant brief card updates on refresh.
  - Rejecting a card with a reason creates a `Preference` fact. Regenerating the brief respects it, and the card explains why. Demo case: Lena rejects the +12.5% Franzbrötchen rise with "too steep, max 8%". The extractor writes `Preference(max_price_increase_pct=8)`. The regenerated card proposes €3.20 → €3.45 (+7.8%, margin 70%, still on target), "Kept under your 8% cap".

### F5. Ask (P1)
- A ⌘K command bar or chat: "Why did we keep less money last week?" Streaming answer, numbers from tools (SQL), citations to facts and queries, and suggested follow-up actions as cards.
- **AC:** numbers in answers pass the number guard; the answer cites at least one evidence source.

### F6. Benchmarks (P0)
- `/bench`: a static page rendered from committed `bench/results/*.json` (works even if the API is down). See §9.

### F7. Offline replay (P0, reliability)
- Golden runs are recorded as event streams plus JPEG frames. If the API is unreachable or `DEMO_MODE=replay`, the UI plays them back with an unobtrusive "Replay" badge. Nothing is ever presented as live when it isn't.

### F8. Mobile owner view (P1/P2)
- Today and Run theater are fully usable at 390 px wide. P2: a WhatsApp-style thread view of the brief.

## 7. UX principles and design direction

**Principles**
1. **One screen, one decision.** Today is three cards, not a dashboard.
2. **Show the work.** Every claim opens to evidence; every action is watchable; every run shows its cost.
3. **Calm by default, cinematic on action.** Brief and memory are quiet and editorial. The run theater is dark, focused and live.
4. **Never surprise the owner.** Dry-run preview before execution, idempotent actions, undo, and explicit "Replay" or "Synthetic data" labels.
5. **Fast feels smart.** Optimistic UI, streamed skeletons, < 100 ms interaction feedback.

**Visual language** (starting point; refine with the `ui-ux-pro-max` skill, then lock tokens in `apps/web/src/styles/tokens.css`)

- **Type:** display serif for € numbers and headings (Instrument Serif); UI sans (Inter or Geist); mono for agent logs (JetBrains Mono or Geist Mono).

- **Signature details:** the agent-cursor halo on the live stream; a skill diff rendered like a code review; € impact in large serif numerals.
- **Accessibility:** WCAG AA contrast, keyboard-complete, visible focus, ARIA live region for run progress.
- **Targets:** Lighthouse ≥ 90 on Performance, Accessibility and Best Practices for `/` and `/bench`. CLS < 0.05.

## 8. Functional requirements (system)

### 8.1 Browser agent
- **Observation:** a Playwright ARIA snapshot of the page, plus a numbered list of interactive elements (`ref`, role, accessible name, label, bounding box), plus URL and title. Screenshots only on heal escalation (vision costs).
- **Action tools (strict JSON schema):** `click(ref)`, `fill(ref, value)`, `fill_secret(ref, secret_key)`, `select(ref, option)`, `press(key)`, `goto(path)`, `wait_for(text|ref)`, `extract(schema)`, `totp(secret_key)`, `done(result)`, `ask_human(reason)`.
- **Secrets** never enter prompts or logs. The model references `secret_key`; the executor resolves it locally and redacts it in events.
- **Domain allowlist** per run (only the target portal origin). Page text is untrusted data: system prompt rules plus allowlist enforcement.
- **Budgets:** max 25 steps and a $0.05 cap per explore run (configurable). Exceeding either triggers `ask_human`.

### 8.2 Skill compiler and replay
- Skill = `{id, portal, version, params_schema, steps[], postconditions[], stats}`. Each step = `{intent, action, target: {role, name}, fallbacks: [{label}|{text}|{css}], value_template, expect: {url_pattern?, visible?, text?}, timeout_ms}`.
- **Compilation** prefers role+name locators, then label/text, then CSS. Literal task values (sku, qty, price) become params. Credentials become secret placeholders.
- **Replay** verifies each step's `expect`. A failure goes to the heal ladder (§F3). Every success or failure updates the stats.

### 8.3 Memory (temporal knowledge graph)
- **Entities:** Business, Product, Ingredient, Supplier, Staff, Shift, Portal, Skill, Preference, WeatherDay, Holiday, Insight, Action.
- **Fact** = `(subject, predicate, object_entity | value_json, valid_from, valid_to, recorded_at, source_episode, confidence)`. This is bitemporal: valid time plus record time.
- **Supersession:** a new fact on the same `(subject, predicate)` with a later `valid_from` closes the previous one.
- **Episodes:** raw inputs (invoice, approval, rejection, chat turn, run result). The extractor (worker model, structured outputs) turns episodes into facts. Structured data (POS, recipes) is written deterministically, with no LLM.
- **Context packer:** task → seed entities → facts valid at `as_of` within 2 hops → rank by (relevance, recency, confidence) → serialise as compact triples under a token budget (default 1,200). The pack ships with the run for display.

### 8.4 Brief pipeline: "agents for judgment, code for math"
1. **Detectors** (pure Python + DuckDB SQL): stock-out forecast, margin erosion, weather-demand. Each emits a `Candidate{kind, evidence[], impact_eur, proposed_action}` with all numbers computed.
2. **Planner** (planner model, structured output): ranks and selects ≤ 3 candidates, writes owner-voice copy using only evidence values, and binds each to a skill + params.
3. **Verifier** (verifier model, `LLM_VERIFIER_MODEL`, default Haiku 5.5): checks each card against `Preference` facts and business rules (price cap, supplier order days). It can veto or adjust within the rules and records its reason.
4. **Number guard** (deterministic): every number in the copy must match a number in the card's evidence (with rounding tolerance). On failure: one regeneration, then fall back to template copy.

### 8.5 Reliability and safety
- Idempotency keys on approve. Run state is persisted (Postgres). SSE with `Last-Event-ID` resume.
- Browser pool: one Chromium process with 2 concurrent contexts and a queue. Hard timeouts per step and per run.
- LLM calls: SDK retries with backoff, refusal handling, and an escalation ladder (§ARCHITECTURE 5).
- Daily spend cap (default $3/day, `LLM_DAILY_BUDGET_USD`). When exceeded, live mode is disabled and replay mode is served.
- Public visitors get replay mode. Live mode needs `?code=<DEMO_ACCESS_CODE>`, or a cookie set by it.

## 9. Benchmarks (the "amazing benchmarks" requirement)

All benchmarks are reproducible with one command (`pnpm bench`). Results are JSON committed under `bench/results/` with model IDs, seeds, n, date and git SHA. **Targets below are goals, not claims. Report whatever we measure.**

| ID | What | Method | Metrics | Target |
|---|---|---|---|---|
| B1 | Browser robustness | 3 tasks (reorder, change price, download invoice) × chaos seeds 0–19 × {cold, warm} | success %, p50/p95 wall time, LLM calls, tokens, $ | cold ≥ 90% at seed 0; heal ≥ 85% across seeds |
| B2 | Learning curve | Same task 20 runs in sequence; portal redesign injected at runs 8 and 15 | per-run latency and $ (line chart: spikes at 8 and 15, then recovery) | warm p50 < 5 s, $0 |
| B3 | Memory vs baseline | 30 questions with SQL ground truth; arms: (a) context pack, (b) raw-dump prompt, (c) no memory | accuracy (±1%), input tokens, $, latency | (a) ≥ 90% accuracy at ≤ 20% of (b)'s tokens |
| B4 (P1) | Model swap | B1-cold subset + B3 on Haiku 5.5 / Sonnet 5.5 / Opus 5.5 | same, per model | inform the default choice |
| B5 | Number guard | All generated briefs during bench | guard pass rate, regenerations | 100% displayed numbers verified |

## 11. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Browser agent flaky on cold explore | Small, well-labelled portals; ARIA snapshot observation; step budget; golden skills pre-compiled before the demo |
| Healing too slow live | Fallback locators first (no LLM); healer model before escalation; demo chaos seed 7 verified at the M2 gate and again in rehearsal |
| Lightsail box down or Wi-Fi bad | Replay mode with recorded golden runs; local `docker compose` backup on the laptop |
| LLM refusal or outage | Escalation ladder plus template copy; replay mode |
| Time overrun | Strict milestone gates ([BUILD_PLAN.md](BUILD_PLAN.md)); cut list in §6 |
| Data realism questioned | Honest labelling of NYC→Bonn re-basing and synthetic weather effect in DATA.md; explain the method |
| Cost runaway | Daily budget cap, per-run caps, replay for the public |
